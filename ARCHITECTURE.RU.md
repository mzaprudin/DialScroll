# Архитектура DialScroll

[English](ARCHITECTURE.md) · [Русский](ARCHITECTURE.RU.md) · [Обзор проекта](README.RU.md)

DialScroll преобразует абсолютный угол магнитного датчика MT6701 в события BLE HID Mouse Wheel на nRF52840. Прошивка объединяет циклическую обработку угла, управление питанием и асинхронную отправку по BLE. `DialScroll` — название проекта, `blescroll` — идентификатор прошивки и настроек, `AirScroll` — имя устройства в Bluetooth.

## Тракт обработки и границы модулей

```text
Колесо + магнит → MT6701
                    ├─ I²C, угол 14 бит → циклический EMA Q8 ─────────┐
                    └─ VOUT → SAADC 12 бит → усечённое среднее ──────┤
                                                                    ▼
                       угол 14 бит → delta кратчайшей дуги → порог
                                                                    ▼
                        опциональное ускорение Q8 → дробный остаток
                                                                    ▼
                       гранулярность → ограниченная очередь Wheel
                                                                    ▼
                                                BLE HID → компьютер
```

| Модуль | Назначение |
|---|---|
| [`src/main.c`](src/main.c) | Порядок запуска и диагностические профили |
| [`src/encoder.c`](src/encoder.c) | Питание, чтение I²C/ADC и расписание idle/active |
| [`src/encoder_math.c`](src/encoder_math.c) | Циклическая фильтрация, ускорение с фиксированной точкой и масштабирование Wheel |
| [`src/scroll_resolution.c`](src/scroll_resolution.c) | Сохраняемые разрешение, ускорение и источник угла |
| [`src/ble_hid.c`](src/ble_hid.c) | Advertising, bonding, HIDS и асинхронная отправка Wheel |
| [`src/battery.c`](src/battery.c), [`src/battery_math.c`](src/battery_math.c) | Измерение аккумулятора и перевод напряжения в процент заряда |
| [`src/diagnostics.c`](src/diagnostics.c) | USB CDC по наличию VBUS, команды и снимки состояния |
| [`src/heartbeat.c`](src/heartbeat.c) | Светодиод состояния через отложенную работу |

Назначения выводов заданы в [`app.overlay`](app.overlay), параметры настройки — в [`include/app_config.h`](include/app_config.h). Математический модуль проверяется отдельно от датчика и Bluetooth.

## Подключение и контроль аккумулятора

Целевая плата — ProMicro-совместимая Tenstar Robot на nRF52840 с UF2-загрузчиком, совместимым с `nice!nano`.

| Сигнал | Подключение |
|---|---|
| MT6701 VDD | 3,3 В через load switch |
| Enable load switch | P0.17, active high, high drive |
| MT6701 GND | Общий GND |
| MT6701 SDA / SCL | P1.00 / P0.11, I²C0 на 400 кГц, адрес `0x06` |
| MT6701 Analog/VOUT | P0.02 / AIN0 |
| Середина делителя аккумулятора | P0.04 / AIN2 |
| Светодиод состояния | P0.15, active high |

Для I²C вход MODE имеет уровень HIGH или использует внутреннюю подтяжку датчика, CSN — HIGH. Эти входы задаются аппаратно. На SDA/SCL включены внутренние pull-up; внешние подтяжки к 3,3 В, обычно 4,7 кОм, поддерживают работу шины на 400 кГц. Развязывающий конденсатор 100 нФ размещается рядом с VDD датчика. Датчик получает питание через load switch, а P0.17 управляет его входом enable. Прямое питание от GPIO используется в кратком стендовом тесте.

Для чтения VOUT выход датчика настраивается в Analog mode. Начальные границы калибровки — ADC-коды `0` и `4095`; параметры `ENCODER_VOUT_MIN_CODE` и `ENCODER_VOUT_MAX_CODE` задают границы по измеренным clamp endpoints. ADC использует `ADC_GAIN_1_4`, `ADC_REF_VDD_1_4`, разрешение 12 бит, acquisition time 10 мкс и значение oversampling `2` в Devicetree. Общее питание датчика и ADC сохраняет ратиометрический характер измерения.

Делитель аккумулятора подключён как `BAT+ → 806 кОм → AIN2 → 2 МОм → GND`:

```text
Vbat = Vadc × 2 806 000 / 2 000 000
```

Канал аккумулятора использует внутреннюю опору, `ADC_GAIN_1_6`, разрешение 12 бит и acquisition time 40 мкс для высокоомного делителя. При обновлении первое измерение отбрасывается, следующие восемь усредняются. Первое обновление назначается через 1 секунду, последующие — раз в 60 секунд. Линейная интерполяция задаёт 0% при 3,30 В, 50% при 3,70 В и 100% при 4,20 В; за границами процент ограничивается крайними значениями. Это настраиваемая начальная кривая для одного Li-ion/LiPo элемента.

Стандартный Battery Service (`0x180F`, Battery Level `0x2A19`) получает новое значение при изменении процента. Его отображение в интерфейсе компьютера зависит от Bluetooth-драйвера ОС. Heartbeat оставляет светодиод выключенным на 8 секунд, затем включает на 150 мс через `k_work_delayable`.

## Получение и циклическая фильтрация угла

Оба источника возвращают угол в общей шкале `0…16383` на один оборот. По умолчанию используется I²C. Одна комбинированная транзакция читает регистры MT6701 `0x03/0x04` и декодирует `(msb << 6) | (lsb >> 2)`.

Тракт I²C применяет экспоненциальное скользящее среднее с состоянием Q8 и α=`64/256`=`1/4`. На каждом шаге фильтр вычисляет кратчайшую циклическую разность между сырым углом и текущим состоянием, вносит поправку и возвращает результат по модулю 16384. Первое чтение инициализирует фильтр. Поэтому переход через ноль следует локальной дуге и сохраняет близость соседних углов.

Тракт ADC получает один угол из восьми чтений:

1. Каждый 12-битный отсчёт переводится в откалиброванную 14-битную шкалу.
2. Отсчёты разворачиваются вокруг первого по разности кратчайшей дуги.
3. Значения сортируются, минимум и максимум отбрасываются, остальные шесть усредняются.
4. Среднее возвращается по модулю 16384.

Например, ADC-коды `4094, 4095, 0, 1` описывают соседние положения около нуля. Циклическая обработка оставляет эту группу около нуля. Для движения используется та же геометрия:

```text
delta = current - previous
if delta >  8192: delta -= 16384
if delta < -8192: delta += 16384
```

Полученная delta задаёт кратчайшее перемещение между чтениями. Пара абсолютных углов позволяет определить движение в пределах половины оборота; idle-период задаёт компромисс между задержкой обнаружения, угловой неоднозначностью и долей времени питания датчика. После обнаружения движения active-режим сокращает интервал чтения.

## Питание датчика и расписание

Обычная работа использует `System ON idle`: RAM и BLE-соединение сохраняются между событиями. `encoder_run()` занимает основной поток и спит до абсолютных дедлайнов; Bluetooth и очереди работ Zephyr выполняются в своих контекстах.

| Состояние или переход | Поведение |
|---|---|
| Нет соединения | Датчик выключен; состояние отслеживания и дробный остаток Wheel сброшены |
| Первое достоверное чтение после boot/reconnect | Установка baseline без Wheel-события; начальный idle-период 200 мс |
| Idle probe | Подача питания, ожидание 33 мс, чтение источника, сравнение с baseline; при неподвижности питание снимается |
| Недавняя активность | Probe раз в 100 мс в течение 10 секунд после последнего движения |
| Установившийся idle | Probe раз в 200 мс |
| Idle → active | `abs(delta) > 32` отсчётов; начальное движение обрабатывается, датчик остаётся включённым |
| Active | Чтения назначаются каждые 2 мс; движение принимается при `abs(delta) > 16` |
| Active → idle | 400 мс без значимого движения; питание снимается, следующий probe назначается через 100 мс |

Подпороговые отсчёты сохраняют опорный угол, поэтому медленное движение накапливается между чтениями. Active-дедлайны сдвигаются на 2 мс; время обработки не добавляется к каждому периоду. Этот период задаёт расписание. GPIO-маркер или временные метки показывают фактический интервал с учётом ADC burst и обработки.

В предыдущем стендовом исследовании четыре захвата запуска VOUT показали переход выхода примерно через **32,62–32,65 мс** после подачи питания. На этом наблюдении основана текущая задержка стабилизации 33 мс. Профиль startup-диагностики позволяет повторить захват с выбранным ADC по процедуре ниже.

Само ожидание стабилизации даёт расчётный вклад в долю включённого времени: 33/200 = 16,5% в установившемся connected idle и 33/100 = 33% в быстром окне. Чтение увеличивает эти значения. Методика стендовой проверки предусматривает отдельное измерение тока всего устройства для advertising, connected idle и активной прокрутки.

## Разрешение Wheel и ускорение с фиксированной точкой

Один обычный Wheel detent соответствует **256 отсчётам** 14-битной угловой шкалы. HID-дескриптор постоянно объявляет Resolution Multiplier ×16. Пользовательский режим меняет гранулярность событий и сохраняет полный путь прокрутки на оборот:

| Режим пользователя | Отсчётов угла на отправляемую порцию | Порция в объявленных единицах ×16 |
|---|---:|---:|
| `off` / ×1 | 256 | 16 |
| ×8 | 32 | 2 |
| ×16, по умолчанию | 16 | 1 |

`encoder_scroll_accumulate()` сохраняет угловой остаток между преобразованиями, в том числе при переходах idle/active во время соединения. `ENCODER_SCROLL_DIRECTION` задаёт знак и сейчас равен `1`. Компьютер включает мелкие единицы записью HID Feature report. Пока эта функция выключена, BLE-слой собирает единицы ×16 обратно в обычные detent. Общая чувствительность сохраняется при разных возможностях хоста и режимах разрешения.

Ускорение — независимая сохраняемая опция, по умолчанию выключенная. После 2048 отсчётов (45°) непрерывного движения в одном направлении коэффициент Q8 линейно растёт от ×1 при 6552 отсчётах/с (примерно 0,4 об/с) до ×2 при 32768 отсчётах/с (2 об/с). Скорость считается по восьми 10-мс корзинам в окне 80 мс; окно продвигают active-отсчёты. Первое перемещение, обнаруженное в idle, отправляется с ×1 и исключается из оценки скорости.

Масштабирование выполняется до преобразования разрешения. Знаковый остаток Q8 сохраняет дробное движение симметрично в обоих направлениях. Реверс, пауза 100 мс, disconnect или смена настройки ускорения возвращают коэффициент к ×1. Нулевые отсчёты продвигают окно скорости и выдают нулевое движение: после остановки ускорение не добавляет прокрутку.

## Отправка BLE и конкурентное выполнение

Устройство предоставляет четырёхбайтовый зашифрованный mouse input report: кнопки/padding, X, Y и знаковый относительный Wheel. Изменяется только Wheel. Однобайтовый Feature report задаёт эффективный множитель хоста: логический `0` означает ×1, логическая `1` — ×16. Boot mouse protocol не содержит Wheel; переход в boot mode очищает ожидающую прокрутку, а report mode восстанавливает отправку.

Advertising использует имя `AirScroll` и `BT_LE_ADV_CONN_FAST_2`. Прошивка поддерживает одно активное соединение и хранит до двух bond. Она запрашивает уровень безопасности L2 и предпочтительные параметры: connection interval 7,5–10 мс, latency 0 и supervision timeout 420 мс. Итоговые параметры выбирает central; диагностика показывает согласованные значения. Обе flash-раскладки используют Bluetooth-стек Zephyr из NCS; имя `sd` обозначает существующую разметку flash.

Транспорт разделяет измерение и отправку:

- Энкодер помещает относительное движение в очередь; отложенная работа Zephyr вызывает API отправки HIDS.
- Mutex защищает активное соединение и режим report. На время отправки удерживается ссылка `bt_conn_ref()`.
- Атомарный накопитель хранит pending Wheel с насыщением ±2048. Сложение использует расширенный промежуточный тип.
- Одновременно отправляется один notification. Каждая отправка забирает до ±127 единиц; callback завершения назначает следующую порцию.
- Ошибки отправки повторяются с интервалом 5 мс. После 25-й неудачной попытки pending-движение очищается и выводится предупреждение.
- Disconnect очищает pending delta, legacy-остаток и состояние notification/retry, затем назначает advertising.

Обновление батареи и heartbeat тоже используют отложенную работу. Прерывание USB-приёмника помещает байты команд в ограниченную очередь сообщений; обработчики work queue меняют настройки и выполняют диагностику вне прерывания.

## Сохраняемые настройки и обработка ошибок

Настройки хранятся в NVS-разделе объёмом 32 КиБ под UF2-загрузчиком, вместе с Bluetooth bonding.

| Ключ | Значения и значение по умолчанию |
|---|---|
| `blescroll/scroll_resolution` | `0`: off, `1`: ×8, `2`: ×16; по умолчанию ×16 |
| `blescroll/acceleration` | `0`: выключено, `1`: включено; по умолчанию выключено |
| `blescroll/encoder_mode` | `0`: I²C, `1`: ADC; по умолчанию I²C |

Функции изменения проверяют вход и публикуют новое runtime-значение после успешного `settings_save_one()`. Отсутствующее или некорректное значение источника сохраняет выбор I²C. Смена источника завершает active-цикл, снимает питание и сбрасывает baseline, EMA, ускорение и угловой остаток. Первое чтение нового источника задаёт baseline. Wheel-события, уже принятые BLE-очередью, продолжают отправляться.

| Событие | Реакция прошивки |
|---|---|
| GPIO питания, SAADC или I²C недоступен | Инициализация энкодера возвращает ошибку |
| Подача питания датчика завершилась ошибкой | Логирование и повтор в следующий idle-дедлайн |
| Ошибка ADC в idle / active | Питание снимается; baseline сохраняется / active завершается с последним достоверным углом |
| Ошибка/NACK I²C | Питание снимается, tracking сбрасывается, следующий probe повторяет I²C; лог выводится не чаще раза в секунду |
| Ошибка записи настройки | Возвращается ошибка, текущая runtime-настройка сохраняется |
| BLE disconnect | Транспортное состояние очищается; после reconnect задаётся новый baseline |
| Старый ключ хоста вызывает ошибку pairing | Этот хост помечается; после disconnect его конфликтующий bond удаляется для новой попытки pairing |
| Ошибка чтения аккумулятора | Последний переданный процент сохраняется, назначается следующее обновление |
| Reset | Tracking инициализируется заново, baseline задаётся до отправки движения |

## Диагностика USB

Обычная прошивка включает USB CDC при наличии VBUS. Логирование изначально выключено, runtime-фильтры источников установлены в `LOG_LEVEL_NONE`. Терминал `115200 8N1` отправляет отдельные байты; необязательные CR/LF игнорируются.

| Байт | Действие в обычной прошивке |
|---|---|
| `h` | Справка, настройки, выбранный/активный источник и последняя ошибка чтения |
| `D` | Включение логов и свежий снимок USB/BLE/энкодера/батареи; повтор даёт новый снимок |
| `d` | Выключение диагностического вывода |
| `0`, `1`, `2` | Сохранение разрешения off, ×8, ×16 |
| `A`, `a` | Сохранение включённого, выключенного ускорения |
| `V`, `v` | Сохранение источника угла ADC, I²C |
| `U` | Переход в UF2-загрузчик через 50 мс (`GPREGRET = 0x57`, cold reset) |

Команды настроек работают при выключенных логах. Отключение USB выключает логи и USB-контроллер, очищает очередь команд и оставляет BLE-прокрутку под обычными правилами соединения. При снятии USB диагностический режим сбрасывается; сохраняемые настройки переживают выключение питания.

Специальные профили включают USB и логи с запуска. `-Diagnostic` запускает энкодер без BLE, `-DiagnosticBle` включает BLE и привязывает питание датчика к соединению. Эти профили выводят поток логов; однобайтовый интерфейс обычной прошивки в них выключен. `-EncoderStartupDiagnostic` ждёт любой байт и собирает до 1024 отсчётов за первые 50 мс питания датчика. CSV с отсчётами печатается после снятия питания; ошибки чтения могут логироваться во время захвата.

Захват запуска использует сохранённый источник угла, по умолчанию I²C. Для захвата VOUT команда `V` в обычной прошивке сначала сохраняет выбор ADC. После прошивки startup-профиля настройка остаётся в NVS; отправка любого байта запускает захват ADC. Команды выбора источника работают в обычной прошивке, а startup-профиль трактует входящие байты как триггеры захвата.

## Разметка загрузки и исправление UF2

Загрузчик читает начальный указатель стека и Reset handler из таблицы векторов приложения. В исходном исследовании сборки NCS 3.2.4 блоки UF2 начинались с `0x26000`, а Reset vector оставался `0x00000C01`. Копирование образа завершалось успешно, но адрес запуска указывал в зарезервированную область SoftDevice.

Исправление линкует приложение по физическому flash-адресу и преобразует полученный Intel HEX через `uf2conv.py` с сохранением адресов. [`CMakeLists.txt`](CMakeLists.txt) создаёт отдельную UF2-цель; `CONFIG_BUILD_OUTPUT_UF2=n` отключает автоматический путь.

| Строка `INFO_UF2.TXT` | Вариант | Область приложения, правая граница исключена | Обычный UF2 |
|---|---|---|---|
| `SoftDevice: S140 6.1.1` | `sd` | `0x26000…0xEC000` | `blescroll.uf2` |
| `SoftDevice: not found` | `nosd` | `0x1000…0xEA000` | `blescroll_nosd.uf2` |

[`tools/verify_uf2.py`](tools/verify_uf2.py) проверяет размер и выравнивание файла, UF2-заголовки, ожидаемый начальный адрес, Thumb-бит и попадание Reset handler в область приложения, а также family ID nRF52840 `0xADA52840`. Скрипт сборки и CI используют этот валидатор. Соответствующая загрузчику раскладка задаёт правильные адреса таблицы векторов.

## Сборка и прошивка

Закреплённая версия SDK — [nRF Connect SDK 3.2.4](https://docs.nordicsemi.com/bundle/ncs-3.2.4/page/nrf/index.html). Команды выполняются в окружении установленного toolchain; `ZEPHYR_BASE` указывает на каталог `zephyr` этого SDK. Сборка использует [sysbuild](https://docs.nordicsemi.com/bundle/ncs-3.2.4/page/zephyr/build/sysbuild/index.html) и плату `promicro_nrf52840/nrf52840/uf2`.

Команды Windows-скрипта из корня checkout:

```powershell
.\build.ps1 sd
.\build.ps1 nosd
.\build.ps1 nosd -Diagnostic
.\build.ps1 nosd -DiagnosticBle
.\build.ps1 nosd -EncoderStartupDiagnostic
```

`-NcsRoot C:\ncs\v3.2.4` явно выбирает установленный SDK. Скрипт находит зарегистрированный toolchain и проверяет полученный образ. Sysbuild называет подкаталог приложения по имени каталога checkout. Для стандартного имени `DialScroll` пути имеют вид:

| Профиль | Результат |
|---|---|
| Обычный `sd` | `build/DialScroll/blescroll.uf2` |
| Обычный `nosd` | `build-nosd/DialScroll/blescroll_nosd.uf2` |
| `nosd`, диагностика | `build-nosd-diagnostic/DialScroll/blescroll_nosd_diagnostic.uf2` |
| `nosd`, диагностика + BLE | `build-nosd-diagnostic-ble/DialScroll/blescroll_nosd_diagnostic_ble.uf2` |
| `nosd`, захват запуска | `build-nosd-startup-diagnostic/DialScroll/blescroll_nosd_startup_diagnostic.uf2` |

Переносимая сборка обычного `sd` из корня checkout:

```sh
APP="$(pwd)"
APP_NAME="${APP##*/}"
west -z "$ZEPHYR_BASE" build --sysbuild -p always \
  -b promicro_nrf52840/nrf52840/uf2 -d "$APP/build" "$APP" \
  -- "-DCONF_FILE=$APP/prj.conf"
python "$APP/tools/verify_uf2.py" \
  "$APP/build/$APP_NAME/blescroll.uf2" --variant sd
```

Для остальных профилей используется соответствующий build-каталог из таблицы выше и следующий порядок файлов `CONF_FILE`. Перед каждым файлом указывается `$APP/`:

| Профиль | Фрагменты конфигурации через `;` |
|---|---|
| Обычный `nosd` | `prj.conf;prj_nosd.conf` |
| `nosd`, диагностика | `prj.conf;prj_nosd.conf;prj_diagnostic.conf` |
| `nosd`, диагностика + BLE | `prj.conf;prj_nosd.conf;prj_diagnostic.conf;prj_diagnostic_ble.conf` |
| `nosd`, захват запуска | `prj.conf;prj_nosd.conf;prj_diagnostic.conf;prj_encoder_startup_diagnostic.conf` |

Кавычки вокруг `-DCONF_FILE=…` сохраняют список с точками с запятой одним аргументом. Эти образы проверяются с `--variant nosd` и соответствующим именем файла.

Прошивка и первое соединение:

1. Двойное нажатие Reset открывает диск `NICENANO`; строка в `INFO_UF2.TXT` определяет вариант. Работающая обычная прошивка также принимает `U` по USB CDC для перехода в загрузчик.
2. Проверенный UF2 копируется на `NICENANO`. При перезапуске платы диск отключается.
3. После pairing с `AirScroll` проверяются оба направления, остановка и reconnect. Первое чтение задаёт baseline.
4. При подключённом USB в serial-порт отправляются `h`, затем `D` для снимка. Команда `d` завершает диагностический вывод.

После изменения HID-дескриптора удаление `AirScroll` на компьютере и повторный pairing обновляют закэшированную report map. Строка `High-resolution Wheel enabled (effective multiplier x16)` подтверждает выбор функции хостом. После сообщения о stale bond повторная попытка pairing создаёт ключ взамен удалённого конфликтующего.

## Автоматические проверки и проверка на устройстве

Два набора ztest содержат **31 тест**: 25 для угловой математики и батареи, шесть для сохраняемых настроек. Они проверяют декодирование, переход через ноль, сходимость EMA, усечённую фильтрацию, дробный остаток, расстояние и гранулярность разрешения, кривую и сбросы ускорения, интерполяцию батареи, перезагрузку настроек и ошибки записи.

```sh
python "$ZEPHYR_BASE/scripts/twister" -T "$APP/tests" \
  -p qemu_cortex_m3 --inline-logs -O "$APP/twister-out"
```

[`ci.yml`](.github/workflows/ci.yml) использует официальный контейнер Nordic с закреплённым NCS 3.2.4. Полный запуск воспроизводится из корня checkout через Docker:

```sh
docker run --rm --entrypoint /bin/bash \
  -v "$PWD:/work/DialScroll" -w /work/DialScroll \
  ghcr.io/nrfconnect/sdk-nrf-toolchain:v3.2.4@sha256:397bac78a3e3825ce30443d4cd28c377ea6e5a28910200820967b648d95f88bb \
  tools/ci.sh
```

[`tools/ci.sh`](tools/ci.sh) загружает окружение toolchain, получает SDK по тегу `v3.2.4` через shallow clone и проверяет коммит `4c3fc0d44534f387a2d623eb1c85cbd2ffc8bcb6`. Он инициализирует west из этого манифеста, исключает Matter, загружает выбранные проекты и фиксирует активный манифест. Затем запускает 10 тестов валидатора UF2 на стандартной библиотеке Python, 31 тест ztest и все пять сборок прошивки, проверяя каждый полученный UF2.

Образы прошивки и соответствующие HEX, ELF и файлы конфигурации собираются в `artifacts/firmware/`. Полный лог сохраняется в `artifacts/ci.log`, зафиксированный манифест — в `artifacts/west-manifest.yml`, отчёты тестов — в `twister-out/`. Тесты валидатора UF2 также запускаются отдельно из корня checkout:

```sh
python -m unittest discover -s tests/uf2 -v
```

Проверка на устройстве охватывает pairing/reconnect, оба направления и переход через ноль, медленное движение, быстрый реверс, смену разрешения, включение/выключение ускорения, смену источника и отключение USB во время BLE-прокрутки. Захват запуска даёт отсчёты с временными метками и ошибками для повторных циклов питания. Ток измеряется от аккумулятора с отключённым USB, отдельно для advertising, connected idle и активной прокрутки. GPIO-маркер вокруг чтения показывает длительность ADC burst и фактический active-интервал; трасса движения до HID показывает задержку отклика. По этим данным настраиваются границы калибровки, пороги движения и период чтения.

## Источники

- MagnTek, [MT6701 Rev.1.8 datasheet](https://www.magntek.com.cn/upload/pdf/202407/MT6701_Rev.1.8.pdf): интерфейсы угла, запуск питания и конфигурация аналогового выхода.
- Nordic Semiconductor, [nRF52840 Product Specification](https://docs.nordicsemi.com/bundle/nRF52840_PS_v1.9/page/keyfeatures_html5.html): SAADC, GPIO и режимы питания.
- Nordic Semiconductor, [документация NCS 3.2.4](https://docs.nordicsemi.com/bundle/ncs-3.2.4/page/nrf/index.html) и [справочник sysbuild](https://docs.nordicsemi.com/bundle/ncs-3.2.4/page/zephyr/build/sysbuild/index.html).
- Исходники по ссылкам выше, [`tests/`](tests/) и [`include/app_config.h`](include/app_config.h) задают реализованное поведение и конфигурацию.
